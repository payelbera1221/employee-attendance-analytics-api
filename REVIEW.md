# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 35-37) | Timezone mismatch: `punch_in` was in UTC, but `shift_start` was parsed as hours and minutes in IST. Calling `punch_in.replace(hour=h, minute=m)` modified the UTC hour instead of IST, throwing off time differences by 5.5 hours. | An employee punching in at 09:35 IST (04:05 UTC) was compared against 09:35 UTC (15:05 IST), yielding negative elapsed time and 0 late minutes. | Implemented `get_attendance_date_and_shifts` which converts `punch_in` to IST timezone before building shift start/end datetimes, and calculates elapsed time using timezone-aware datetimes. |
| 2 | `compute_late_minutes` (lines 37-38) | Off-by-one grace period calculation (R2): `minutes = int((punch_in - start).total_seconds() / 60); return minutes if minutes > 10 else 0`. At 09:40:01 for a 09:30 shift, elapsed time is 601s, `minutes = 10`. Because `10 > 10` is False, it returned 0. Per R2, grace period is 10:00 (600s), and any punch strictly more than 10:00 after shift start must return total whole minutes elapsed (floor) since shift start (10 minutes). | Punch-in at 09:40:01 for a 09:30 shift returned 0 instead of 10. | Evaluated `delta_seconds > 600`; if true, returned `int(delta_seconds // 60)`, otherwise 0. |
| 3 | `compute_late_minutes` (lines 34-38) | Overnight shift unaware (R1): For overnight shifts (e.g., 22:00 - 06:00), an employee punching in after midnight (e.g., 00:30) had `punch_in.replace(hour=22, minute=0)` set to 22:00 on the same calendar day (21.5 hours in the future), resulting in negative elapsed time and 0 late minutes. | Punch-in at 00:30 IST for a 22:00 shift produced 0 late minutes instead of 150. | Computed shift start relative to the shift's starting date (the previous day for post-midnight punches before `shift_end`), correctly calculating elapsed minutes. |
| 4 | `compute_work_hours` (line 42) | Banker's rounding instead of half-up (R4): `round((punch_out - punch_in).total_seconds() / 3600, 2)` used Python's built-in `round()`, which rounds half to even. | A duration of 9630 seconds (2.675 hours) rounded to 2.67 instead of 2.68. | Used `decimal.Decimal` with `ROUND_HALF_UP` to round exact seconds / 3600 to 2 decimal places. |
| 5 | `compute_overtime` (line 48) | Missing 30-minute threshold (R3): `return max(0, int((punch_out - end).total_seconds() / 60))` returned any positive overtime, ignoring R3 which states overtime is counted only if at least 30 minutes, otherwise 0. | Punch-out at 18:45 for an 18:30 shift end returned 15 overtime minutes instead of 0. | Enforced `minutes if minutes >= 30 else 0`. |
| 6 | `compute_overtime` (lines 46-47) | Overnight shift end set on wrong date: `end = datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)`. For an overnight shift starting on `2026-07-06` (22:00 to 06:00), `date_str` is `2026-07-06`, so `end` was set to `2026-07-06 06:00` (16 hours before shift start) instead of `2026-07-07 06:00`. | Punch-out on an overnight shift generated massive false overtime (> 1400 minutes). | If `shift_end <= shift_start`, shifted the `shift_end` date forward by 1 calendar day relative to the attendance date. |
| 7 | `compute_overtime` (line 48) | Offset-naive vs offset-aware datetime crash: `end` was constructed with `tzinfo=IST`, while `punch_out` loaded from MongoDB without `tz_aware=True` was naive UTC, raising `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Calling `compute_overtime` with a database-fetched datetime crashed with an unhandled 500 TypeError. | Configured `MongoClient(..., tz_aware=True)` and standardized all instant arithmetic on timezone-aware datetimes. |
| 8 | Client initialization & Startup (lines 23-25) | No indexes created on startup, and no lifespan context manager. Without indexes, queries perform full collection scans (`COLLSCAN`), fail `/admin/explain` tests, and cannot enforce database-level uniqueness constraints under concurrency. | GET `/admin/explain` returned `COLLSCAN` plans; duplicate creates caused data corruption. | Added a FastAPI `lifespan` handler that idempotently creates indexes on startup for both `employees` and `attendance_logs`. |
| 9 | `POST /employees` validation and response (lines 54-61, 86-98) | Inadequate input validation (no regex for `emp_code`, no check that `shift_start != shift_end`), and returned `created_at` as a Python `datetime` object instead of integer epoch milliseconds per `openapi.yaml`. | Allowed identical shift start/end times; response JSON serialized `created_at` as ISO string instead of integer epoch ms. | Added Pydantic field patterns, model validator ensuring `shift_start != shift_end`, and serialized `created_at` to epoch milliseconds. |
| 10 | `GET /employees` ordering & serialization (lines 101-109) | Did not sort by `emp_code` ascending as required by OpenAPI spec, and returned raw documents containing `created_at` datetime instead of epoch ms. | Employees were returned in arbitrary MongoDB insertion order; `created_at` serialized as datetime string. | Added `.sort("emp_code", 1)` and serialized `created_at` to integer epoch ms. |
| 11 | `POST /attendance/punch-in` instant validation & overnight date (lines 117-125) | Did not validate `punched_at` range or strict type (accepted seconds-looking values, strings, floats without 422). Also, did not apply R1 overnight shift rule: punch-ins before `shift_end` for an overnight shift were assigned to current day instead of previous day. | Punch-in at 01:00 for a 22:00-06:00 shift got assigned to the wrong date; passing seconds like `1600000000` did not raise 422. | Used strict Pydantic `EpochMillisType` (`ge=100000000000, le=4102444800000`) and applied R1 shift logic to subtract 1 day for post-midnight overnight punches. |
| 12 | `POST /attendance/punch-in` race condition (lines 126-127) | Check-then-insert pattern: `if db.attendance_logs.find_one(...): raise 409`. Under concurrent punch-ins, both checks pass before either insert occurs, causing duplicate records or uncaught 500 errors. | Sending concurrent punch-in requests produced multiple records or unhandled errors. | Created a unique compound index on `{"emp_code": 1, "date": 1}` and caught `DuplicateKeyError`, converting it to HTTP 409. |
| 13 | Extra / Missing fields in attendance responses (lines 147, 182) | Injected illegal `"id": str(d.pop("_id"))` field into responses. The schema and `DATA_MODEL.md` explicitly state records have no `id` (identified by natural key `(emp_code, date)`). Also failed to convert `punch_in`/`punch_out` to epoch milliseconds. | Response schema validation failed against `AttendanceRecord`. | Removed `id` field completely and formatted `punch_in` and `punch_out` as integer epoch milliseconds. |
| 14 | `GET /attendance` filter validation & sort order (lines 164-179) | If `date_from > date_to`, returned 200 with empty list instead of raising 422. Also sorted only by `date` descending, omitting the secondary sort by `emp_code` ascending. | `GET /attendance?date_from=2026-07-10&date_to=2026-07-05` returned 200 instead of 422; records on same date were not sorted by `emp_code`. | Added validation returning 422 when `date_from > date_to`, and sorted by `[("date", -1), ("emp_code", 1)]`. |
| 15 | `GET /health` control flow (line 83) | Dead code: Redundant `return {"status": "ok"}` after `except` block. | Static code analysis / linter warning. | Cleaned up control flow. |
